Start with what you already know

An eval is QA with a test environment

You already know the core job: define good support, review a case against it, calibrate the reviewer, and use the result to improve quality.

Traditional support QA

Reviews work after it happened

  • Samples real conversations
  • Uses a support scorecard
  • Finds coaching and process gaps
→

AI support eval

Can test work before release

  • Runs fixed practice cases
  • Checks actions as well as words
  • Can block a known bad change
The shift is not from “human QA” to “machine scores.” The shift is from sampling replies to testing complete support decisions.

The reusable framework

Five layers, each with one job

The technical names matter only when you need to connect a product. In support language, this is a repeatable QA room.

The practice caseScenario

The customer goal, starting product state, evidence available, and the ending that counts as safe.

The product translatorAdapter

Turns that product’s chats, actions, screens, calls, handoffs, and final state into one common journey.

The QA scorecardEvaluation profile

Selects the checks that fit this product: investigation, safety, action, handoff, voice, or another support concern.

The QA sessionRunner + release gate

Runs every requested case, keeps failures visible, and stops a release when a serious rule is broken.

The audit recordTrace + JSON + HTML

Saves what happened and why. Langfuse can hold a review copy, but the local evidence remains the source of truth.

The framework behind the framework

Ten patterns, grouped into five support jobs

The old Atlas listed ten methods one by one. These groups show when a support team would use them.

Create trustworthy cases

Pre-build gate: test the assumption that makes the product worth building.

Hidden answer keys: keep the expected truth away from the system being tested.

Adversarial cases: include polished cases designed to slip past the checker.

Judge the risky parts

Narrow judge panel: review grounding, process, promises, diagnosis, and handoff separately.

Deterministic gates: use fixed rules for hard facts and let models advise at the edges.

Review the work of support

Investigation grading: reward facts, unknowns, useful next checks, and waiting for evidence.

Journey outcome: verify the action, final product state, and handoff—not only the reply.

Test each weak link

Support-shaped benchmarks: judge whether the component changes the support outcome, not whether it wins a generic benchmark.

Retrieval, classification, and detection: test whether the right knowledge, intent, and sensitive details survive.

Keep the proof honest

Pre-set release bars: decide what “good enough” means before looking at the result.

Control plane: decide which evaluations run on a code change, a release, research work, or a new product connection.

Version seal: refuse to combine results from parts that did not actually run together.

The value of the experiments

What I am learning

The numbers belong in the evidence. These are the decisions the evidence changed.

If it works on clean practice language, it understands customers.

Synthetic customers can flatter a weak system.

Generated cases are good for repeatability. They are not proof that the system understands messy, indirect, emotional customer language.

A correct final cause means the troubleshooting was good.

Being right too early is still bad support.

The agent must earn a diagnosis from the evidence available at that point. A lucky guess is not a safe support method.

An AI reviewer can replace a broad human QA pass.

The reviewer needs its own QA.

Use model judgment for meaning. Use direct checks for tool calls, product state, timing, and required fields. Calibrate the judge with humans later.

A convincing reply proves the customer was helped.

The product state proves the action.

“You’re all set” is only a claim. Resolution means the promised change happened or the customer reached a clear next step.

Healthy components add up to a healthy support system.

Green parts do not prove a green journey.

The tested versions must be the versions that ran together. A stale seal, missing review layer, or incomplete journey should block the combined claim.

Voice added one more lesson: the transcript is not the call. Hearing, timing, interruption, silence, repetition, action, and outcome all shape the customer experience.

The claim boundary

What is true now—and what is not true yet

This is the part to use in an interview, article, README, or conversation with a support leader.

True now

A serious local support-eval framework exists

  • It runs complete fictional chat journeys and saved voice journeys.
  • It separates cases, product connectors, QA checks, release rules, and evidence.
  • It catches the known failure patterns represented in its cases.
  • It can connect to another saved or sandboxed support product through an adapter.
  • It records failures, errors, incomplete work, and unsafe outcomes instead of hiding them.

Not true yet

It is not a production-proven QA system

  • It has not reviewed real customer traffic or a real support queue.
  • It has not proved an effect on CSAT, resolution, effort, cost, or safety.
  • It cannot yet detect drift between its practice cases and real customer behaviour.
  • Its AI reviewers have not been calibrated at scale against a production QA team.
  • Its voice pack does not place calls or judge real telephony and audio quality.
Do not say: “I evaluated fifteen production support products.” Say: “I extracted and tested an evidence-gated support QA method across local components, experiments, and controlled journeys.”

Evidence-gated journey QA

A support decision should not pass QA unless the journey contains the evidence needed to defend it. Ask what the system knew, whether that was enough, whether the action happened, and whether the customer reached a safe next state.
